# Frontend Controlled Deferred Write Wrappers

Date: 2026-06-27

## Scope

This document tracks frontend API exports and protected ThinkPHP wrapper routes for copied Vue write controls that are visible or reachable, but whose real business behavior is still deferred.

The remaining wrappers return Java-style JSON envelopes with `code = 400`. They do not call service-layer write methods, write database rows, update balances, move inventory, start workflow, delete records, read provider credentials, change schema, or modify Java source.

- Expenditure-record direct `add/delete` is now bounded manual expense maintenance backed by settlement-account quick expense rows. `/biz/bizexpenditurerecord/edit` is a narrow payer-time/category correction that syncs only the linked statement timestamp, and `/biz/bizexpenditurerecord/edit/account` is a narrow account switch that moves the stored expenditure amount between settlement accounts and syncs the linked statement account.
- Collection-receipt direct `add/edit/delete` is now bounded row maintenance for receipt rows linked to active payment records. `/biz/bizcollectionreceipt/batchExpenditure/edit` remains the only route in this module that creates repayment expenditure/statement rows and updates receipt settlement from finance activity.
- Debit-note direct `add/edit/delete` is now bounded row maintenance for debit-note rows linked to active expenditure records, with delete blocked when settlement or history amounts exist. `/biz/bizdebitnote/batchRepayment/edit` remains the loan-repayment route that creates payment/statement rows and updates debit-note settlement, and `/biz/bizdebitnote/history/add` remains the debit-note-only historical insert with no payment/expenditure/statement or balance side effects.
- Purchase-order direct `add`/`delete` is now bounded row maintenance: add creates the order and product-item rows only, while delete only logically deletes orders that have not completed settlement, entered warehouse, generated goods expenditure, or generated delivery rows. `/biz/bizpurchaseorder/cancel` is a narrow status marker, `/biz/bizpurchaseorder/edit` updates only order amount and existing purchase-order item amount/cost fields, `/biz/bizpurchaseorder/audit/edit` keeps the same field whitelist with Java-compatible completed/expenditure bypass, `/biz/bizpurchaseorder/warehouse/one/add` is the single-order warehouse stock-in path, and `/biz/bizpurchaseorder/warehouse/add` is the batch warehouse stock-in path for completed not-in-warehouse orders. Expenditure creation, settlement statements, workflow start/approval, stock rollback delete behavior, Java data-change events, and notification side effects remain deferred.
